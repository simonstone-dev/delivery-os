# 验证范围

发布时分别回答三件事：工具能不能运行、记录是否一致、方法是否改善真实项目判断。

## 可复现的工具检查

```bash
python -m unittest discover -s tests -v
python scripts/verify_release.py
```

行为测试覆盖两种语言的README流程、空目录与已有目录、移动后独立运行、来源去重与版本、哈希变化、错误引用及数值、2000任务依赖链、依赖环、单价缺失、小数运算、报告重算、签认元数据和过早移交拦截。

发布检查核对本地链接、声明的双语配对、案例编号与估算约定、版本引用、技能前置字段和有限公开文件卫生扫描。它不联网检查、不保证识别所有敏感数据模式，也不能自动证明翻译语义完全相同。

CI配置为Windows、Ubuntu、macOS的Python 3.10及3.12。实际远程结果以Actions为准，配置矩阵不等于已全部执行。本地结果见[发布验证记录](../../examples/release-verification.md)。

## 场景判断标准

合成案例有意包含未确认AI摘要、部署冲突、样本缺失、价格未知，以及尚未实现业务系统等情况。有效解读应做到：

1. 保留两种模板、人工审核的一期边界。
2. 不把执行付款加入本期方案。
3. 把部署冲突交给有权限的客户IT负责人确认。
4. 样本与评分规则不足时，OCR保持未验证。
5. 不编预算、单价、审批和测试证据。
6. 来源、需求、工作包、验收相互关联。
7. 先讲业务，再讲实现。
8. 验收待定，不能提前宣称可以移交。

见[人工编写的案例解读](../../examples/scenario-review.zh-CN.md)。数据和解读由维护者编写，测试核对机制与明确边界，**不是独立模型评测**、真实项目成功率，也不证明任何AI都会正确执行。

## 怎样证明实际效果

真实项目中记录首轮遗漏、澄清次数、返工及原因、估算与实际人天、外部等待、合格输出质量和AI辅助总投入。比较相同范围与质量标准，说明基线是实测还是估计。客户资料保持私有，仅公开获准且脱敏的结果。

本项目不宣称统一估算准确率、AI提效比例或保证交付成功。记录完整有助于控制项目，但不能代替业务正确性。
