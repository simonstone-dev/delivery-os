# 从资料到交付的工作流程

版本 0.2.0。以下为按项目风险裁剪的内部方法，不是认证标准或统一法规。一个阶段可以并行调查多个问题；完成条件用于判断承诺成熟度，不要求用户逐项批准日常可逆工作。

## 总体安排

售前工作包括理解、调查、初案与估算；签约后按已确认范围继续细化、开发与交付。客户要求先交初案时，可以先给带假设和验证计划的版本；不能把完整生产验证作为所有售前材料的前提。关键技术风险高时，可建议独立调研验证阶段及其费用。

| 阶段 | 核心行动 | 可检查的成果与结束条件 |
|---|---|---|
| 0 接收与机会判断 | 识别客户目标、决策人与实际使用人，登记所有资料，确认本次期限与提交要求 | 资料索引、范围草案、提交清单；能说明做什么、为什么、给谁、当前要求交什么；可建议不承接 |
| 1 项目与业务理解 | 还原现状、目标、数据和规则，现场或远程走查代表性任务，核对价值基线 | 一页理解、现状与目标流程、名词解释；正常、异常和更正有去向，用户能复述关键流程 |
| 2 需求与验收定义 | 分清正式要求、建议和假设，明确输入规模、质量、权限、接口、安全、性能、运维和验收 | 需求—交付—验收关联；本期/后期明确，关键矛盾有处理，明确谁能确认业务规则及验收 |
| 3 技术调查与验证 | 比较成熟方案、复用/采购/开发选项；排除不符合硬约束的路线；对高影响未知做小试验 | 有依据的推荐与备选、架构、验证记录；知道能做至何程度、还需什么条件，失败有处置 |
| 4 实施与商务基线 | 按成果拆任务、估人天，核人员、依赖、日历、外部费用、维护和付款条件 | 可核算的人天和费用、阶段计划、责任与假设；初估和可承诺版本区分，缺口不伪装闭合 |
| 5 迭代开发与集成 | 每轮选真实业务的一段完整链路，按需求开发、评审和测试，定期演示并收反馈 | 输入到输出可运行，包含必要权限、异常与记录；需求变更经影响分析，版本可恢复 |
| 6 业务验证与上线准备 | 历史回放、样本外验证、试点或影子运行，做迁移演练、备份恢复和回退检查 | 验收记录、缺陷处理、上线条件与回退安排；业务负责人和技术负责人在职责内确认 |
| 7 上线、移交与结项 | 受控切换，按项目需要观察运行，交培训、源码、配置、手册和维护责任 | 正式版本与交付清单、验收及移交记录；按合同跟踪阶段款与尾款，未结事项有负责人 |
| 8 运营复盘与退出 | 回收实际工作量、效果和持续成本；计划升级、续维、归档或服务退出 | 估算偏差及原因、AI 净提效、实际价值；数据导出、账号回收和留存按约定处理 |

## 资料处理与证据

原始文件保留，提取文本、OCR、截图识别结果和摘要保存为派生资料并指向原件。阅读登记包含文件版本、页/表/单元格/时间点、解析方式、覆盖范围与问题。长文件按业务主题分批读，先全量盘点，不一次吞入全部历史。

每个来源至少记录 `id/title/path/sha256/read_status/origin_group/authority`。同一会议的多个摘要标同源，不能算独立验证；AI 纪要不是逐字稿。取自正式文档也只证明文档中如此表述，不证明接口可用、预算已承诺或方案已达标。

每个结论标明：资料记载、已确认、分析推断、待验证或存在冲突；“已确认”要有确认人、职责、时间和适用范围。摘要与原件冲突时回看原件，同时检查是否有较新授权变更；不能仅凭文件日期机械决定优先级。只有来源元数据缺失时，记录缺口而不是编造。

## 业务理解的方法

每条核心业务用一个真实例子串起：发起角色→输入材料→判断和计算→处理动作→输出→审核→执行→更正。说明业务顺序与开发顺序的区别。对跨系统数据，核稳定编号、单位、状态、生效日期与版本；样表的公式和历史结果都可能有错。

先拿能完整关联的一个业务包，再补差异与异常。要求客户保留电子原件公式、隐藏表、宏和关联关系；脱敏时保持关联编号一致。不要要求客户为交资料重新制作技术文档；可以由经办人演示，AI 整理后请其校准。

## 需求与提交要求

需求包括功能与非功能要求，也包括客户配合、团队资质或案例、驻场、支持期限、交付格式和可退出条件。提交清单记录每项“是否必交、本轮是否交、对应文件、缺口”。本轮尚未交的必交项不能因已有 PPT 或初案就标成完成。

验收写清：数据集和版本、规模、环境、计时起止、分子分母、阈值、异常/无解如何计分、复核与签认人。客户的“零错误”“最优”“全覆盖”“实时”等措辞都需要定义。精度、自动覆盖率、最终业务结果、人工工时和现金收益分别衡量。

## 技术与 AI 判断

架构先回答系统边界、数据怎么流、各模块责任、运行与部署、失败恢复、权限审计和维护归属。需要时参考成熟架构框架检查遗漏，不因框架存在就全部填满。按规模从足够简单的实现开始，新增复杂度应有现实理由。

区分 AI 辅助交付与产品内置 AI。后者逐项判断适用性、质量、时延、调用或本地成本、数据边界与人工接管。对严格计算优先确定性规则或求解器，大模型做识别、理解或解释；这是任务特性判断，客户另有约束时以有效约束为准。

对外部依赖核对：许可证与附加条款、数据/模型/权重各自许可、版本兼容、接入权限、限流、成本、维护活动与服务承诺。公开页面可访问不等于正式 API 或稳定商业服务。研究判断、本机验证和生产试点分别记录，未试验的明确写明。

## 试验与停止条件

优先验证“如果失败就会改变方案或承接”的假设。每次记录问题、成功标准、固定输入与版本、环境、步骤、原始结果、资源与人工投入、观察、限制及下一决策。复用旧证据前核适用性；旧版本或不同输入的结果不能直接迁移。

跨模型/方案比较尽量固定数据和业务边界；改变输入、时长、构图或硬件就标为不同用例。多项同时改变可作为组合方案比较，不能单独归因其中一项。失败后先定位，满足信息增量或修复理由才重试；长耗时任务保留准确状态与接续记录。

## 项目控制与职责

由一个项目负责人维护总计划，明确业务规则、技术实现、安全、验收和运维各自责任。是否并行人员或多个 AI 执行者按当前授权与收益决定，不能把角色清单等同于实际有人。共享环境或昂贵资源需要唯一调度入口及幂等记录，具体并发数依项目决定。

每周或约定节奏关注成果、偏差、风险与需要决策的事项；原型演示用于取得反馈，不自动改变已确认范围。变更记录来源与授权、影响的需求/技术/任务/测试/成本/里程碑、处理决策、生效版本和负责人。日常内部修正可直接做，外部承诺按已有授权处理。

## 四种状态分开

- 实现状态：尚未实现／部分实现／已实现。
- 技术验证：未测试／通过／失败／受限。
- 业务验收：待验收／通过／拒绝／附条件。
- 上线状态：未准备／准备中／获准／已上线／已回退。

任务成功响应、完整解码或页面可打开，只支持相应技术结论。主观质量需要实际观看和相应验收；不能用技术成功替代。

## 持续改进

每个里程碑记录估算与实际、等待与返工原因、被遗漏需求、外部依赖成本和验收失败。将重复出现且有证据的经验脱敏后提议升级方法，并给出改变哪个判断、如何减少遗漏或返工的依据。不把具体客户的硬约束、固定时长或历史单价升级成通用默认。
